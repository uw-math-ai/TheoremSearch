# Handoff: better retrieval for the lean-graph premise benchmark

Status: ready. All assets live in RDS `v2` under model_names and prompt_names
listed below. Tested end-to-end on MathlibQR — see
`leansearch_v2_comparison.md` §6a for the headline numbers (+19pp Recall@10,
+16pp nDCG@10 over the bare-slogan baseline; beats LSv2 retriever-only).

---

## TL;DR

We've shipped five orthogonal retrieval improvements on top of the existing
slogan-embedding setup. They're additive at the SQL/query layer — no schema
changes, no re-index. Drop them into the lean-graph premise retrieval path
and you should see most of the QR-side bump carry over (the graph-expand
lever in particular is purpose-built for "gold premise = parent edge of the
cosine winner," which is what lean-graph's labels are).

The full retrieval harness with every lever is at
`experiments/leansearch_v2_replication/run_eval_v2.py` (CLI flags
`--dedupe --ann-k 1000 --hybrid-trigram --hyde ensemble --graph-expand`).
Lift the inner functions; the SQL is parameterized and reusable.

## The five levers (with SQL snippets)

All assume you already have the standard temp-table pattern for filtering
HNSW shortlists by `external_id ∈ {Mathlib_v427, Mathlib_v428}`:

```sql
CREATE TEMP TABLE lean_slogan_ids AS
SELECT s.slogan_id
FROM slogan s
JOIN statement st ON st.statement_id = s.statement_id
JOIN paper p      ON p.paper_id     = st.paper_id
WHERE s.model_name = 'qwen3-235b'
  AND NOT s.insufficient_context
  AND p.external_id IN ('Mathlib_v427','Mathlib_v428');
CREATE INDEX ON lean_slogan_ids (slogan_id);
ANALYZE lean_slogan_ids;

-- and these GUCs (touch a vector first to register them):
SELECT '[1]'::vector(1);
SET hnsw.iterative_scan = relaxed_order;
SET hnsw.ef_search = 500;
```

### Lever 1 — `--ann-k 1000` (was 200)

Just bump the binary-HNSW shortlist size. Cheap; +ttiny latency. Lets the
later rerank/dedupe steps actually have something to fuse.

### Lever 2 — `--dedupe` (one slot per decl, not per slogan)

After cosine returns top-K candidates (each tagged by `statement_id`),
collapse to the FIRST occurrence of each statement_id. With the ensemble
model_name above, each decl shows up twice (once per prompt) and dedupe
fuses them — biggest single win for free.

```python
seen, out = set(), []
for c in candidates:
    if c["statement_id"] not in seen:
        seen.add(c["statement_id"]); out.append(c)
```

### Lever 3 — `--hybrid-trigram` (gated to name-like queries)

For queries that look like a Lean decl name (≤ 4 words, no LaTeX, ≤ 40 char),
run a parallel `pg_trgm` similarity search on `formal_metadata.decl_name`,
RRF-fuse with cosine. Catches "lattice" → `Lattice` cases where cosine
hands back `Lattice.iSup_eq` instead.

```sql
SELECT statement_id, decl_name, similarity(decl_name, %(q)s) AS sim
FROM formal_metadata fm
JOIN statement st ON st.statement_id = fm.statement_id
JOIN paper p ON p.paper_id = st.paper_id
WHERE p.external_id IN ('Mathlib_v427','Mathlib_v428')
  AND decl_name %% %(q)s
  AND similarity(decl_name, %(q)s) >= 0.5
ORDER BY sim DESC
LIMIT 200;
```

(Build a GIN trigram index on `formal_metadata.decl_name` once.)

### Lever 4 — `--hyde ensemble`

Ask qwen3-235b for a 2–4 sentence Mathlib-doc-style description of the
query, embed THAT with the `DOC_INSTRUCTION` prefix, run a second cosine
search, RRF-fuse with the original. System prompt is in
`run_eval_v2.py:HYDE_SYSTEM`. ~$0.0005/query via Nebius.

For premise retrieval this likely helps most because the NL query and the
gold premise's slogan share little surface form — HyDE rewrites in
doc-comment style so both vectors land in the right neighborhood.

### Lever 5 — `--graph-expand` ★ MOST RELEVANT FOR YOUR BENCHMARK

For each top-K cosine candidate, surface its `formal_dependency` parents
along `extends`/`field`/`sig` edges. RRF-fuse those parents back into the
candidate list using the child's rank as the parent's pseudo-rank.

This is essentially "if cosine retrieved `Functor.IsEquivalence`, also
consider `Functor` as a candidate." Your lean-graph labels ARE these
parent edges, so this directly converts cosine's structural-similarity
hits into the labels you're scoring against.

```sql
SELECT DISTINCT
    fd.src_id::text          AS child_id,
    parent.statement_id::text AS parent_id,
    parent_fm.decl_name      AS parent_decl_name
FROM formal_dependency fd
JOIN statement parent ON parent.statement_id = fd.dep_id
JOIN paper p ON p.paper_id = parent.paper_id
JOIN formal_metadata parent_fm ON parent_fm.statement_id = parent.statement_id
WHERE fd.src_id = ANY(%(child_ids)s::uuid[])
  AND fd.edge_type IN ('extends','field','sig')
  AND p.external_id IN ('Mathlib_v427','Mathlib_v428')
  AND parent_fm.decl_name IS NOT NULL;
```

Note: this is the SAME `formal_dependency` table your benchmark labels are
derived from. Using it on the retrieval side is fair (labels are
sig/extends/field; we expand by those same edges to surface candidates).
If you want it cleaner, restrict the edge_types you expand by to a
DISJOINT subset of what defines your labels — but in practice the lever's
effect is "use the graph at query time, not just at scoring time."

## Things specifically to validate on lean-graph's benchmark

The MathlibQR bump (+19pp Recall@10) was on QR-style queries (paraphrase
the gold decl). lean-graph's premise retrieval is closer to "find what
this theorem DEPENDS on," so:

- **Graph-expand direction.** Our current code expands UP the dep graph
  (parents of cosine winners). lean-graph's labels are "decls this
  statement uses" — same direction *if* the user's query describes the
  using-statement, opposite direction if the query describes a single
  premise. Verify which is which for your eval and flip
  `fd.src_id` ↔ `fd.dep_id` in `GRAPH_EXPAND_SQL` if needed.
- **MathlibMPR finding.** When we ran MathlibMPR (separate LSv2 benchmark,
  also premise retrieval) the levers actively HURT vs baseline (0.142 vs
  0.190 group_recall@10). HyDE writes in main-theorem voice, which pulls
  retrieval toward sibling theorems instead of toward the premises.
  Suggest validating each lever independently against your N=388k
  benchmark before turning them all on at once.
- **The learned head still wins.** Your 0.54 Recall@100 from the learned
  query head is well above what our 0.16 baseline → 0.X retrieval boost
  can realistically reach. The relevant comparison is whether our boost
  + your learned head beats your learned head alone — likely yes for the
  named-concept queries, plausibly no for the structurally-tricky ones.

## What I'd do first if I were extending this

1. **Drop the temp-table + ensemble-model-name pattern into your existing
   retrieval path.** Single SQL change; should give you most of the +12pp
   nDCG bump from row 7 (lsv2 ensemble + all retrieval-side levers).
2. **Add graph-expand with edges flipped to match your label semantics.**
   This is the lever I expect to disproportionately help lean-graph
   specifically.
3. **Skip HyDE for premise retrieval** until you've isolated whether it
   helps or hurts (MPR showed it hurts).
4. **Re-evaluate against the learned head.** The interesting number is
   "learned head + our retrieval boost vs. learned head alone," not
   "our retrieval boost vs. cosine baseline."

Ping me if anything in the harness doesn't make sense — most of the
non-obvious bits (HNSW iterative scan, signed-int hash modulo bug, Nebius
API path for non-GPU embed) are documented inline.
